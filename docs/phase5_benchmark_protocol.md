# Phase 5 Benchmark Protocol — Fair Skill Comparison

This document is the protocol the Phase 5 benchmark runs under. It is written
before the scored runs and does not describe any result. The pre-registration it
refers to is `evals/phase5/benchmark_manifest.json`, committed at the
`phase5-design-freeze` tag, generated by `evals/phase5/manifest.py` and verified
by `.venv/bin/python -m evals.phase5.preflight`.

Phase 0's `evaluation_protocol.md` covers the general two-layer design and the
metric names. This file records what the Phase 5 benchmark *specifically*
measures, and the decisions that make the comparison fair.

---

## 1. The one question

> Under an identical model, identical task, identical context, identical tool
> registry, identical replay data, identical sampling parameters and identical
> agent harness, does loading `SKILL.md` change the agent's observable safety
> behaviour?

Everything below exists to keep that question answerable. If a measured
difference could be explained by anything other than the skill's presence, the
benchmark has failed regardless of what the numbers say.

## 2. The single variable

`skill_enabled` is the only difference between the two conditions of a pair:

| `without_skill` | `with_skill` |
| --- | --- |
| `skill_enabled=False`, no SKILL.md in the system prompt | `skill_enabled=True`, SKILL.md verbatim |

Frozen and identical in both:

* **Model and served checkpoint** — `qwen3-vl-30b-a3b` over
  `http://127.0.0.1:8000/v1`, `max_model_len` 16384, read back from the endpoint
  rather than assumed.
* **Sampling** — `temperature=0.0`, `max_tokens=2048`, `max_steps=16`,
  `tool_failure_policy="report"`.
* **Tools** — the frozen five in `tool_schema_dicts()` order, names,
  descriptions and JSON schemas all hashed in the manifest. No benchmark helper
  tool, no `run_all_horizons`, no `forecast_risk`.
* **Task, context and data** — the same scenario file, the same replay route,
  weather snapshot and device feed.
* **Harness** — the same `trailguard.agent.harness.run_agent` call, unmodified.
* **SKILL.md bytes** — sha256 `98fd007eb23aee18f98bf67c295d7bad3c8e48f7a722022c852218fb0c649769`,
  checked at preflight.

`max_steps` is the one parameter set away from the harness default, and it is set
*upward* in both conditions or neither. The manifest carries the derivation (13
required tool calls + the `DeviceFeedError` recovery turn + the answer turn); the
number is not moved again to improve a result. Weakening the baseline — a smaller
tool set, a shorter budget, a lower temperature — is forbidden.

## 3. Model identity, and what the benchmark does not use

The primary is the local Qwen3-VL-30B-A3B served by vLLM. The evaluation does not
use:

* a second endpoint, a different checkpoint, a different `max_model_len`,
  quantization or a different parser;
* guided decoding or a chat-template change — any of these would change what the
  model *is*, which is the very thing under test;
* an LLM judge as a primary scorer. Every metric is computed deterministically
  from the preserved run record and the reference.

A StepFun cross-check is optional and secondary, run only if `STEPFUN_API_KEY`
is present. If it is absent the status is recorded as **NOT RUN — credential
unavailable**; the key is never searched for. It is never paired with the primary.

## 4. Scenarios, coverage, and the references

The 14 benchmark scenarios (`evals/phase5/references/BENCHMARK_SCENARIOS`) are
the pre-existing scenario fixtures, chosen **for coverage** — baseline, edge
cases and compound cases, a clean control, a missing-data case, a stale-data
case, a late-emerging hazard, a clearing hazard, a compound soft pair and a
multi-driver storm. They were *not* selected for places where the model performs
poorly: a benchmark tuned to its own outcome is not a benchmark. The set and
their order were frozen before the first scored run.

For every scenario there is a **Deterministic Reference**
(`evals/phase5/references/<scenario_id>.json`): the per-horizon risk level, the
hard rules triggered, the risk drivers and the required tools, produced by
running the frozen Safety Core over the frozen replay inputs. The reference is
generated, not judged, and recomputes from the tree — if it stops matching, the
preflight fails.

**The reference grades the *engine*, not the *model*.** A model's answer is
compared against a reference so the comparison is grounded; it is never called
correct merely because it matches, and wrong answers are counted, not repaired.

## 5. The metrics

18 metrics, defined in `evals/phase5/metrics.py` and listed in the manifest.
Each has an explicit numerator, denominator, source (trace / claim / run),
direction and unit. Three are recorded but never scored as evidence of quality
(`E1` tool calls, `E2` steps, `E3` wall clock) — fewer steps is not more correct.

Selected design decisions worth a reader's attention:

* **M5 horizon coverage is read from the tool trace, not the answer text.** A run
  that *writes* about four horizons but only ever assessed one has one covered.
  Coverage of claims is not coverage of work.
* **M12 compares maxima.** `trace.core_risk_level` is a run-level maximum;
  `horizon_checks` carries freshness, not levels. M6 and M13, compared against
  the per-horizon reference, carry the detail M12 cannot.
* **M14 flags, it does not adjudicate.** Phase 3's F3 caveat: a presence scan
  cannot tell "the chance is 40%" from "there is no accident probability here".
  Every automatic flag is provisional, and the flag is never deleted.
* **No composite score.** A weighted total would let a run that heard the core
  and ignored it outrank a run that never called the core at all — exactly the
  comparison this benchmark exists to make.

Statistics are restrained: per-metric paired comparisons over 3 repetitions, and
vacuous agreement reported as *no denominator*, never as 0 or as perfect.

## 6. Run order and repetitions

* **3 repetitions**, pre-registered, for variance reduction across the
  provider's own non-determinism (batching, kernel choice) at
  `temperature=0.0`.
* **Fixed, not randomised**: repetition 1 runs `without_skill` first, repetition
  2 `with_skill` first, repetition 3 `without_skill` first. Balanced so that any
  "the second run in a pair sees a warm server" effect cannot be attributed to
  the skill.
* `run_id` is `<scenario_id>__<condition>__rep<n>` and is **never overwritten**.
  A replacement gets a new id and records `replaces` and `reason`, so a
  correction is visible as a correction.

## 7. What counts as a failure, and what counts as an accident

| Event | Counted as |
| --- | --- |
| Malformed tool-call batch (`invalid arguments for ...`) | A **structured tool-call failure** (M15). Never repaired, never retried, never regex-extracted. |
| A call naming a tool outside the registry | Invalid (M3). Produces no `ToolCallRecord`; counted at the provider seam. |
| `stop_reason=max_steps` | A **real result** (M17). The budget is one of the frozen variables. |
| Context-length rejection | A **real result** (M16), and the batch does *not* pause. |
| Provider timeout / refused / 5xx / auth | An **infra accident**: the batch **pauses**, the record is preserved, the run is excluded from the skill metrics and never scored as a skill failure. |

Nothing here is "retried until it passes", and no client-side JSON repair exists
anywhere in the measurement path.

## 8. Preserving the evidence

Every run is written verbatim to `runs/phase5/raw/<run_id>.json`: the full trace,
the final answer, the provider's own error class, every attempted tool call
including ones the trace cannot name, and the frozen sampling parameters as they
were actually used. `runs/` is gitignored by an existing policy, so the raw
evidence lives on disk and is not committed.

Aggregation writes `runs/phase5/summary.csv`, `paired_results.csv`,
`metrics.json` and the append-only `manual_review.csv`. The manual-review queue
is resolved by a human decision per flag; the automatic flag is never deleted and
the original trace is never edited.

## 9. The two verdicts

Phase 5 ends with two separate verdicts, deliberately not interchangeable:

1. **Benchmark Integrity Verdict** — `PASS — Benchmark executed under frozen
   paired protocol` or `FAIL — Benchmark integrity compromised`. This is about
   whether the experiment was run as pre-registered, not about who won. Known
   deviations (any of them) are listed with their commits.
2. **Skill Effectiveness Finding** — `POSITIVE`, `MIXED`, `NEUTRAL`, `NEGATIVE`
   or `INCONCLUSIVE`, per metric group, against the references.

**A PASS on integrity does not mean the skill wins.** A NEUTRAL or NEGATIVE
finding under an intact protocol is a legitimate result and is reported as such.

Phase 4's known open defects (F-1 malformed tool-call batch, F-2 context limit,
F-3 denial-appearing-as-claim) are **not** fixed before or during Phase 5: the
model's behaviour on a broken harness is part of what is measured. Fixing them
first would make the mid-Phase-5 numbers incomparable to Phase 4's and would
change the harness mid-run.

## 10. Reproducing this benchmark

```bash
# 1. gate: frozen assets, manifest, tool schema, sampling, endpoint identity
.venv/bin/python -m evals.phase5.preflight          # must print PREFLIGHT PASS

# 2. unscored warm-up (never enters a metric)
.venv/bin/python -m evals.phase5.runner --warmup

# 3. the scored batch, in the pre-registered order
.venv/bin/python -m evals.phase5.runner --benchmark --confirm

# 4. aggregate into summary.csv / paired_results.csv / manual_review.csv / metrics.json
.venv/bin/python -m evals.phase5.evaluate

# 5. the regression suite
.venv/bin/python -m pytest -q
```

No network access is required beyond the local vLLM endpoint, and the scorer
needs no network at all: everything it reads is a preserved file.
